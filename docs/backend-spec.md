# EcoKart Backend Build Spec

This file says what backend work is being built, in what order, and how we will know each step is finished.
`docs/system-design.md` stays the source of truth for the architecture, the tables, and the flows.
This file is the working plan on top of it.

How this file is used:

- Before a step starts, its section below is written with what will be built and how it will be checked.
- If something changes while a step is being built, its section is updated in the same change, and the change is added to the change log at the end.
- When a step is finished, its status in the build order table changes to Done.
- If a step changes a decision in the design doc, the design doc is updated in the same change.

## How the backend runs

EcoKart does not have a separate Express server.
The design (sections 2 and 4) puts the backend in three places, and all three are TypeScript on Node.js.

| Part | Where | What it does |
| --- | --- | --- |
| Web app | `apps/web` | Next.js route handlers (`/api/...`) and server actions answer every request from the browser, the Razorpay webhook, and Better Auth at `/api/auth/*`. |
| Worker | `apps/worker` | A plain Node.js process that takes jobs from the pg-boss queue: AI calls, embeddings, emails, imports, PDFs, and scheduled jobs. |
| Core | `packages/core` | All business rules, the database schema, migrations, and clients for outside services. The web app and the worker both call it. |

Next.js is itself a Node.js server, so adding Express would mean a second server doing the same job.
Keeping the API inside Next.js gives one deployable web service, one set of sessions, and one place where permissions are checked.

## Step 1: Database foundation

Status: Done (5 October 2026).

### Goal

A fresh database can be created with one command, it holds every table from design doc section 5, and the database itself enforces who can see and change which rows.
The web app and the worker start against it with their own restricted database users.

### What gets built

1. **Drizzle schema for all 36 tables**, one file per domain in `packages/core/src/db/schema/`.
   The four Better Auth tables (`users`, `sessions`, `accounts`, `verifications`) are generated by the Better Auth CLI from our auth configuration and are never edited by hand.
   The other 32 tables follow section 5 column by column.
2. **SQL migrations** in `packages/core/src/db/migrations/`, generated by drizzle-kit, plus two hand-written migrations for what Drizzle cannot describe: extensions, database roles, helper functions, grants, and triggers.
3. **Two database users for the running programs.**
   `ecokart_web` is used by the web app and is subject to row-level security.
   `ecokart_worker` is used by the worker and has a policy on every table that lets it see and change all rows.
   Migrations run as the database owner, which is the only user that can change the table structure.
4. **Row-level security policies** on every table that holds buyer or seller data (listed below).
5. **A request context helper**, `withContext`, that opens a transaction and sets `app.role`, `app.user_id`, `app.seller_id`, and `app.guest_token` for that transaction only.
6. **A migration command**, `pnpm db:migrate`, that applies new migrations, sets the passwords of the two database users, installs or upgrades the pg-boss job queue tables, and grants the two users access to them.
   It is safe to run again and does nothing when everything is up to date.
7. **The web app and the worker connect with their own users.**
   The worker no longer changes the job queue tables when it starts; it checks they are installed and stops with the message "The job queue tables are missing or out of date. Run `pnpm db:migrate`" if they are not.
8. **Automated tests** that build a fresh test database with the real migrations and check the row-level security rules and the schema rules.

### Database users and access

| User | Used by | Can change table structure | Row-level security |
| --- | --- | --- | --- |
| Database owner (`ecokart` locally, the RDS master user in AWS) | `pnpm db:migrate` only | Yes | Not applied, because it owns the tables |
| `ecokart_web` | Web app | No | Applied: sees only what the current request may see |
| `ecokart_worker` | Worker | No | A `worker_all` policy on every table allows every row |

The design doc said the worker uses a role that bypasses the policies.
On Amazon RDS the master user cannot create a role with the `BYPASSRLS` attribute, so the worker gets the same effect from an explicit full-access policy on each table.
This works the same way locally, in CI, and on RDS.

Each user gets only the table privileges it needs.
For example, neither user can UPDATE or DELETE rows in `seller_ledger_entries`, `order_events`, or `audit_logs`, and triggers also block UPDATE and DELETE on those three tables for every user, including the owner.
The ledger also refuses TRUNCATE.

### Request context

Every web request that touches buyer or seller data runs inside `withContext`, which sets four values with `set_config(name, value, true)`.
That is the parameterised form of `SET LOCAL`, so the values disappear when the transaction ends and are safe with transaction-mode connection pooling.

| Value | Meaning |
| --- | --- |
| `app.role` | `anonymous`, `buyer`, `seller`, `admin`, or `system` |
| `app.user_id` | The signed-in user, empty for anonymous visitors |
| `app.seller_id` | The seller the signed-in seller account belongs to |
| `app.guest_token` | The guest cart cookie, so a guest can reach only their own cart |

`admin` and `system` can see and change every row.
`system` is for work that changes several parties' data at once, after the service has checked permissions itself.
For example, confirming a payment writes the buyer's order, each seller's ledger entries, and each seller's invoice number in one transaction, and the Razorpay webhook that triggers it has no signed-in user.
Checkout, payment confirmation, order expiry, cancellation, and refunds run as `system`; every later step that uses it says so in its section.

### Row-level security rules

"Full access" means `app.role` is `admin` or `system`.

| Table | Who can see a row | Who can add or change a row |
| --- | --- | --- |
| `addresses` | The owning buyer; full access | The owning buyer; full access |
| `sellers` | Anyone, if approved; the seller's own account; full access | Add: full access. Change: the seller itself; full access |
| `products` | Anyone, if approved and not deleted; the owning seller; full access | The owning seller; full access |
| `product_variants`, `product_images` | Anyone who can see the product | The owning seller; full access |
| `product_moderation` | The owning seller; full access | Add: the owning seller; full access. Decide: full access |
| `product_embeddings` | Anyone who can see the product | Worker only |
| `carts`, `cart_items` | The owning buyer, or the guest holding the cart's token; full access | Same |
| `orders` | The buyer; any seller with an item in the order; full access | Full access (the buyer may add their own) |
| `order_items` | The buyer of the order; the seller of that item; full access | Add: full access. Change: the seller of that item; full access |
| `shipments` | The buyer of the order; the shipping seller; full access | The shipping seller; full access |
| `order_events` | Anyone who can see the order, limited to the items they can see | Anyone who can see the order (append only) |
| `return_requests` | The buyer; the seller of the item; full access | Add: the buyer. Decide: full access |
| `invoices` | The buyer of the order; the issuing seller; full access | Full access |
| `payments`, `refunds` | The buyer of the order; full access | Full access |
| `payment_events` | Full access | Full access |
| `seller_ledger_entries` | The seller; full access | Full access (append only) |
| `reviews` | Anyone, if published; the author; full access | The author; full access |
| `catalogue_imports`, `catalogue_import_rows` | The seller; full access | Seller adds imports; the worker processes rows |
| `ai_requests` | Shared cache rows (no user, no seller) for anyone; otherwise the owning user or seller; full access | Same |
| `search_queries`, `email_outbox`, `audit_logs` | Full access | Anyone may add a row (append only) |

Tables with no buyer or seller data have no row-level security, and the application checks permissions for them: `categories`, `brands`, `coupons`, `platform_settings`, `content_pages`, and `rate_limits`.
The four Better Auth tables also have none, as the design doc says, because only Better Auth reads and writes them.

### Smaller decisions made in this step

- **Drizzle 0.45 (the current stable release)**, not the 1.0 release candidate, which has not had a release since June 2026.
  Better Auth 1.7 supports both, so moving to 1.0 later is a contained change.
- **Timestamps.**
  Section 5.1 says every table has `created_at` and mutable tables also have `updated_at`.
  Where a table listing in section 5 left one out, it is added: `brands`, `product_images`, `product_moderation`, `product_embeddings`, `shipments`, `invoices`, `catalogue_imports`, `catalogue_import_rows`, `ai_requests`, `platform_settings`, `email_outbox`, and `rate_limits`.
  `payment_events` keeps `received_at` from the design doc as its creation time.
  A database trigger keeps `updated_at` current on every change, so it is right even for changes made with raw SQL.
- **Better Auth tables store times as `timestamp` without a time zone**, because that is what its CLI generates.
  The values are UTC, and only Better Auth reads them.
- **`users.role` has a CHECK constraint** allowing `buyer`, `seller`, and `admin`, matching the one-role-per-account decision.
- **`sessions.impersonated_by` is `text`**, not `uuid` as section 5.3 listed, because that is what Better Auth generates.
- **Invoice prefixes are 1 to 6 capital letters or digits**, so a full invoice number can stay within the 16 characters GST allows (see the open points below).
- **State codes are the two-digit GST state codes** (for example `27` for Maharashtra), because the first two digits of a GSTIN use the same codes and GST place of supply is decided by comparing them.
- **Money in TypeScript** is read from the `bigint` columns as a JavaScript `number` holding whole paise.
  That is exact up to about ₹90 lakh crore, far beyond any order, and avoids converting `BigInt` values for JSON.
  All money arithmetic stays in whole paise.
- **Database checks that protect money and stock**, in addition to the ones listed in section 5:
  an order total equals subtotal minus discount plus delivery;
  an order line total equals unit price times quantity, and its taxable amount plus tax equals the line total minus its discount share;
  an invoice uses either CGST plus SGST or IGST, never both;
  a coupon can never be used more times than its limit;
  a ledger entry's sign matches its type (sales and commission reversals positive; commissions, refund reversals, and payouts negative).
- **Extra unique rules** that make retries safe: one default address per buyer, one invoice prefix per seller, one row per spreadsheet row in an import, one record per Razorpay refund id, and one text embedding per product.
- **Keyset pagination indexes** from section 5 include `id` as a tie-breaker where the sort column is not unique.
  Each later step adds the indexes its own screens need.
- **Full-text search uses the `english` text search configuration**, so "bottles" also matches "bottle".
  Keyword search in step 9 must use the same configuration.
- **The job queue tables are installed by `pnpm db:migrate`**, using pg-boss's own `migrate` command, so the web and worker users never need permission to create tables.
  Queues must be created without the `partition` option, because a partitioned queue creates a table at runtime.
- **Database passwords are sent to PostgreSQL already hashed** (SCRAM-SHA-256), so a plain password never appears in a statement that the database might log.
- **Tests use their own databases**, one per package (`ecokart_test_core`, `ecokart_test_web`, `ecokart_test_worker`), rebuilt from the real migrations at the start of every test run.
  The development database is never touched by tests.

### Not in this step

- Better Auth's HTTP route, OTP sending, and session handling (step 2).
  This step only adds the auth configuration needed to generate the four tables.
- Seed data such as platform settings, categories, and content pages (steps 3, 5, and 16).
- The order number sequence (step 12) and any service functions.

### Done when

- `pnpm db:up` then `pnpm db:migrate` builds every table on an empty database, and running `pnpm db:migrate` again reports that nothing changed.
- `pnpm dev` starts the web app and the worker with their own database users, and `http://localhost:3000/api/health` reports the database as ok.
- The tests prove the row-level security rules for anonymous visitors, buyers, sellers, administrators, guests, and the worker, and that every table follows the schema rules.
- `pnpm check` passes.

### Open points found in this step

- GST rules limit an invoice number to 16 characters.
  The format in section 5.7, `{seller prefix}/{FY}/{sequence}` with a year like `2026-27`, can go over that.
  Step 14 will propose a shorter format (for example `ABC/2627/000123`) for the client's chartered accountant to confirm.
- An OTP email queued in `email_outbox` would hold the code in plain text in the payload.
  Step 2 will make sure the code is never stored readable, for example by keeping it out of the stored payload.
